产品概述

第一层理解：这个项目是什么、解决什么问题

D3 Visuals 是一个可视化参考实验室。它收录了十二种不同视觉家族（flow / hierarchy / network / spatial / temporal / distribution / scalar field / cyclical）的场景实现，每个场景对应一个独立的激励性问题。项目的核心目的不是输出可复用的图表组件，而是展示 D3 作为几何计算与布局引擎的能力——把数据映射成形状、路径与颜色。

项目通过 catalog.json 对场景进行元数据登记，每个场景有唯一 id、用途类别、复杂度和标签。所有场景共享同一套画布尺寸（1400×900）和同一套六色主调色板，保证视觉一致性。

  • 12 种视觉家族覆盖流、层次、网络、空间、时序、分布、标量场、周期等八大家族
  • 程序化数据所有数据均由数学函数合成，零外部依赖，离线可复现
  • SVG 输出纯 SVG 渲染，支持透明背景导出，便于嵌入文档
  • 像素级验收基于 Playwright 的端到端测试：透明度、可见像素、色彩丰富度三重校验
  • 交互合约每个场景必须响应 pointer 事件，测试脚本验证交互计数递增
  • 离线友好构建与测试完全离线，网络请求被 Playwright 路由拦截

架构解读

项目采用「单文件核心 + 外部管线」的极简架构。src/main.ts 是唯一的源代码文件，内含场景调度逻辑和全部 12 个渲染函数。每个渲染函数内部直接调用 D3 的布局算法（chord / tree / voronoi / force / treemap / partition / stack / contours 等），将合成数据映射为 SVG 元素。

渲染管线 scripts/capture.mjs 扮演质量关卡的角色：它启动 Vite 开发服务器，用 Playwright 以无头 Chrome 逐个加载场景，等待 window.__VIS_READY__ 就绪标志后截图，并对 PNG 做像素级校验（透明度占比、可见像素占比、色彩丰富度），同时验证交互事件合约。

场景家族与布局引擎

第三层理解：12 个场景如何按视觉家族分组，分别调用哪些 D3 能力

家族与引擎映射

12 个场景分属八个视觉家族，各自调用 D3 不同的布局原语。层次家族（3 个场景）基于 d3.hierarchy，分别用 tree / treemap / partition 三种布局算法表达同一数据结构的不同几何形态。网络家族（2 个场景）则分别用 d3.forceSimulation 力导向和邻接矩阵两种方式表达协作关系。

值得注意的是 beeswarm 场景，它并非调用独立的 beeswarm 布局器，而是借用 d3.forceSimulation 的 collision 力来实现点的非重叠排布——体现了项目「D3 是几何工具包」的核心定位。

主走查：场景渲染与像素验收

端到端场景：从命令触发到 PNG 输出的完整链路

主走查 · 渲染验收闭环

运行 npm test 触发的完整流程，覆盖构建、浏览器渲染、交互验证与像素验收四个阶段。

  1. TypeScript 类型检查tsc --noEmit 编译期校验。通过后进入构建，失败则整条测试链提前终止。
  2. Vite 构建 + 开发服务器启动capture.mjs 子进程启动 Vite（指定端口，如 4176），监听 stdout 中就绪标志，超时 15 秒抛出异常。
  3. Playwright 逐个加载场景遍历 catalog 中的 12 个 scene id，按 ?scene=xxx 打开页面；路由拦截所有非本地请求，确保离线。
  4. 就绪等待 + 透明截图等待 window.__VIS_READY__ === true（15 秒超时），对 #stage 元素执行 omitBackground: true 截图，输出到 out/。
  5. 交互合约验证读取 __INTERACTION_COUNT__ 初值，模拟两次鼠标移动后再次读取，要求计数严格递增，否则判定交互失效。
  6. 像素级三重验收用 pngjs 解析输出 PNG，统计：透明像素 ≥ 8%、可见像素 ≥ 3.5%、色彩丰富像素 ≥ 2500。任一不达标则场景失败。

走查要点

整条测试链的设计哲学是「视觉项目的可观测性」。对于以图形为输出的项目，传统单元测试难以覆盖渲染质量，因此项目采用像素级验收作为主要质量防线：透明度下限保证背景确实透明（而非白底），可见像素下限保证画面不为空，色彩丰富度下限保证不是单色噪点。

交互合约（interaction contract）是另一层保障：每个场景的 SVG 根元素必须监听 pointer 事件并递增全局计数器。这确保了场景不只是静态图像，而是具备基本交互响应能力的活的可视化。

设计决策

关键的架构取舍与原因

单文件核心 vs 多模块拆分

全部 12 个场景的渲染逻辑集中在 src/main.ts 一个文件中，没有拆分为独立模块。这个选择的理由是：每个场景的代码量不大（10–25 行），且共享调色板、标题工具、画布尺寸等基础配置，拆分会增加导入层级和心智负担。对于示例型项目，集中式布局更便于横向比较不同视觉家族的实现方式。

合成数据 vs 真实数据

所有场景使用数学函数（sin / cos / 模运算 / 随机分布）合成数据，不依赖任何外部数据源。这保证了：① 构建完全离线可复现；② 输出图像稳定，像素验收不会因数据变化而误报；③ 项目聚焦于可视化表达本身，而非数据获取或清洗。代价是场景缺少真实叙事深度，但作为参考实验室这是有意的取舍。

Playwright 像素验收 vs 快照对比

测试方案选用「像素统计阈值」而非传统的「快照像素对比」。原因在于力导向图（force network）等场景的布局有一定随机性，严格像素对比会产生大量误报。统计阈值（透明度、可见面积、色彩丰富度）既能抓住渲染失败（空白、全黑、纯色），又对布局抖动有足够容忍度。
